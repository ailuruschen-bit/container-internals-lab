# Docker イメージのビルド実践（3）：キャッシュ、ARG/ENV、.dockerignore

[English](../docker-image-build-cache-args-ignore.md) | [中文](../zh/docker-image-build-cache-args-ignore.md) | **日本語**

これまでの 2 回の実験で、「イメージをどうビルドするか」は解決した。今回はさらに、ビルドの過程そのものを観察する。Docker が繰り返しのビルドを高速化できるのはなぜか、ビルド段階と実行段階にそれぞれ異なる変数をどう渡すのか、そしてビルドコンテキストにどのファイルを含めるかをどう制御するのか、である。

この 3 つの実験は互いに独立しているように見えるが、実際にはすべて同じことに影響している。**どの入力がイメージのビルドに関わり、入力が変わったときにどの手順を再実行する必要があるのか**ということである。

## 1. ビルドキャッシュを観察する

1 つ目の実験では、次のような Dockerfile を使った。

```dockerfile
FROM alpine:latest

RUN apk add --no-cache curl

WORKDIR /app

COPY message.txt .

CMD ["cat", "message.txt"]
```

ビルド時に `--progress=plain` を付ける。

```bash
docker build \
  --progress=plain \
  -t cache-lab:v1 .
```

デフォルトの進捗表示は動的に更新されるが、`plain` はビルドの各手順を通常のテキストとしてすべて出力する。そのため、各手順がキャッシュにヒットしたかどうかを観察しやすい。

初回のビルドでは、すべての手順を実際に実行する必要がある。Docker は再利用できるビルド結果を保存しておく。Dockerfile もビルドの入力も変わっていない状態で同じコマンドを再び実行すると、出力に次のような表示が見られる。

```text
CACHED
```

`--progress=plain` は出力の表示方法を変えるだけで、キャッシュを有効にしたり無効にしたりするものではない。ビルドキャッシュはもともとビルダーの一部である。

### キャッシュが無効になる理由

Dockerfile の各ビルド手順は、前の手順の結果と、現在の命令の入力に依存している。

```text
FROM
  ↓
RUN apk add curl
  ↓
WORKDIR /app
  ↓
COPY message.txt .
  ↓
CMD ...
```

`message.txt` だけを変更すると、`COPY` の入力が変わるので、以前の結果はもう使えない。その前にある `RUN apk add` は影響を受けないので、引き続きキャッシュにヒットする。しかし `COPY` より後の手順は新しい上位の結果に依存しているため、通常はこの新しい経路にもとづいて再計算が必要になる。

したがって、Dockerfile の順序は繰り返しのビルドの速度に直接影響する。実用的な原則は次のとおりである。

> 比較的安定していて実行コストの高い手順を前に置き、頻繁に変わる内容を後ろに置く。

たとえば、アプリケーションのソースコードは頻繁に変わるので、安定したシステムの依存関係をインストールするより前に `COPY . .` を書くべきではない。

```dockerfile
FROM alpine:latest

RUN apk add --no-cache curl

WORKDIR /app
COPY message.txt .

CMD ["cat", "message.txt"]
```

こうしておけば、`message.txt` を変更しても `curl` を再インストールする必要はない。

実際のプロジェクトでは、依存関係をさらに分けることもできる。たとえば、まず依存関係のマニフェストをコピーして依存関係をインストールし、頻繁に変わるソースコードは最後にコピーする。こうすれば、コストの高い依存関係のインストール手順を再実行する必要があるのは、依存関係のマニフェストが変わったときだけになる。

既存のキャッシュを明示的に使わないようにするには、次のようにする。

```bash
docker build --no-cache -t cache-lab:v1 .
```

ただし、日常のビルドで習慣的にキャッシュを無効にするべきではない。より価値があるのは、Dockerfile の順序をうまく組み、キャッシュが無効になる範囲をファイルが実際に変わった範囲にできるだけ一致させることである。

## 2. `ARG`：ビルド段階のパラメーターを渡す

2 つ目の実験では、まず Dockerfile でビルド引数を宣言する。

```dockerfile
FROM alpine:latest

ARG BUILD_LABEL=experiment

RUN echo "build label: $BUILD_LABEL"
```

`ARG` のデフォルト値は `experiment` である。そのままビルドすると、以降のビルド命令がこの値を読み取れる。

```bash
docker build \
  --progress=plain \
  -t lab-env:v1 .
```

コマンドラインでデフォルト値を上書きすることもできる。

```bash
docker build \
  --build-arg BUILD_LABEL=release \
  --progress=plain \
  -t lab-env:v2 .
```

ここで起きているのは、新しいビルド引数の入力である。そのため、`BUILD_LABEL` を使っている手順は既存のキャッシュを使えなくなる可能性がある。

`ARG` の有効範囲はイメージのビルド過程である。ビルド段階で使われたからといって、自動的にコンテナ実行時の環境変数になるわけではない。

## 3. `ENV`：イメージのデフォルトの環境変数を保存する

同じ Dockerfile に、次の記述を加えることもできる。

```dockerfile
ENV RUN_MODE=production

CMD ["sh", "-c", "echo RUN_MODE=$RUN_MODE; echo BUILD_LABEL=${BUILD_LABEL:-unset}"]
```

全体の関係は、次のように簡略化できる。

```dockerfile
FROM alpine:latest

ARG BUILD_LABEL=experiment
ENV RUN_MODE=production

RUN echo "build label: $BUILD_LABEL"

CMD ["sh", "-c", "echo RUN_MODE=$RUN_MODE; echo BUILD_LABEL=${BUILD_LABEL:-unset}"]
```

イメージを実行する。

```bash
docker run --rm lab-env:v1
```

次のような結果が得られる。

```text
RUN_MODE=production
BUILD_LABEL=unset
```

この結果からわかること：

- `RUN_MODE` は `ENV` によってイメージの設定に書き込まれており、コンテナを作成したときにもデフォルトで存在する。
- `BUILD_LABEL` は `ARG` によってビルド段階に提供されただけで、自動的に実行環境に入ることはない。

また、`ENV` は実行段階でしか参照できないわけではない。Dockerfile で宣言した後は、以降のビルド命令からも読み取れる。`ARG` との重要な違いは、`ENV` がさらにイメージのデフォルトの環境変数として残ることである。

コンテナの実行時には、デフォルト値を上書きできる。

```bash
docker run --rm \
  -e RUN_MODE=development \
  lab-env:v1
```

今度はコンテナから次のように見える。

```text
RUN_MODE=development
```

`-e`（`--env`）が変更するのは新しいコンテナの実行設定であり、元のイメージにある `RUN_MODE=production` をさかのぼって変更するわけではない。次に `-e` を付けずにコンテナを作成すれば、イメージのデフォルト値が使われる。

### `ARG` と `ENV` の関係

| 比較項目 | `ARG` | `ENV` |
|---|---|---|
| 主な用途 | ビルドのパラメーター | イメージとコンテナの環境変数 |
| Dockerfile の以降のビルド手順から読み取れるか | できる | できる |
| デフォルトでコンテナの実行環境に残るか | 残らない | 残る |
| コマンドラインでの上書き方法 | `docker build --build-arg` | `docker run -e` |

ビルド引数をイメージのデフォルトの環境変数に変換したい場合は、その受け渡しを明示的に書く必要がある。

```dockerfile
ARG APP_VERSION
ENV APP_VERSION=$APP_VERSION
```

こうして初めて、`APP_VERSION` が最終的なイメージの設定に入る。

ただし、`ARG` も `ENV` も、パスワード、トークン、秘密鍵を渡すのには適していない。ビルド引数はビルドの記録やメタデータに現れる可能性があり、`ENV` はイメージの設定に直接保存される。機密情報は、変数名で隠そうとするのではなく、専用のビルド時シークレットや実行時シークレットの仕組みを使って扱うべきである。

## 4. `.dockerignore`：まずビルドコンテキストを絞り込む

3 つ目の実験では、次の Dockerfile を使った。

```dockerfile
FROM alpine:latest

WORKDIR /app

COPY . .

CMD ["ls", "-la", "/app"]
```

`COPY . .` の範囲は広い。1 つ目の `.` はビルドコンテキストで使える内容を、2 つ目の `.` はイメージの現在の作業ディレクトリを表している。

プロジェクトのディレクトリに、ソースコードと一緒にログ、一時ファイル、ローカルのツール用ディレクトリなどがあると、すべてをそのままコピーすることで不要なファイルまでイメージに入ってしまう可能性がある。

ビルドコンテキストのルートに `.dockerignore` を作成できる。

```text
.git
*.log
tmp/
secret.txt
```

次にビルドするとき、これらのルールに一致する内容はビルドコンテキストの準備段階で除外されるので、その後の `COPY . .` でもコピーされなくなる。

目的は `.gitignore` と似ており、どちらもルールによって処理したくないファイルを除外するものである。ただし両者は別のツールに属しており、具体的なマッチングのルールが完全に同じだと単純に考えるべきではない。

`.dockerignore` がもたらす効果は次のとおり。

- ビルダーに送るコンテキストの内容を減らす。
- 無関係なファイルが `COPY` でイメージに入るのを防ぐ。
- 無関係なファイルの変更によって `COPY` のキャッシュが無効になるのを減らす。
- ローカルのログ、バージョン管理のディレクトリ、機密ファイルを誤ってパッケージ化するリスクを下げる。

最後の点は特に重要だが、`.dockerignore` は誤って含めることを防ぐ保護層の 1 つにすぎず、完全なシークレット管理の仕組みとして扱うべきではない。本物の認証情報は、そもそも通常のビルドコンテキストに置かず、イメージのレイヤーにも書き込まないのが望ましい。

### `.dockerignore` とキャッシュの関係

ここで話は 1 つ目の実験に戻る。

プロジェクトに、絶えず変化する `debug.log` があるとする。それが `COPY . .` の入力に含まれていると、ログが変わるたびに、アプリケーションのコードがまったく変わっていなくても、このレイヤーのキャッシュが使えなくなる可能性がある。

`*.log` を `.dockerignore` に書いておけば、ログはこの `COPY` の入力に含まれなくなり、ログの変化によってこの手順のキャッシュが無意味に壊されることもなくなる。

つまり、`.dockerignore` はイメージの内容を小さくするだけでなく、本当に変わった入力をビルダーがより正確に判断する手助けもしている。

## 5. 今日得られた理解

この 3 回の実験は、1 本のビルド入力の流れとしてつなげることができる。

```text
プロジェクトのディレクトリ
    │
    │ .dockerignore で絞り込み
    ▼
Build Context
    │
    ├── Dockerfile の命令
    ├── COPY が使うファイル
    └── --build-arg で渡す引数
              │
              ▼
       ビルドキャッシュの判定
              │
              ▼
         Docker Image
              │
              ├── ARG はデフォルトでは実行環境に入らない
              └── ENV はデフォルトの環境変数として保存される
                          │
                          ▼
                    docker run -e
                    コンテナ作成時に上書きする
```

ビルドキャッシュは単純なグローバルのスイッチではなく、各命令とその入力の上に成り立つ再利用の仕組みである。前のある手順の結果が変われば、後続の手順が依存する土台も変わる。

`ARG` と `ENV` も、同じ種類の変数の 2 通りの書き方ではない。`ARG` は主にビルドをどうパラメーター化するかという問題を扱い、`ENV` はビルドに関わったうえで、さらにコンテナのデフォルトの実行環境になる。

`.dockerignore` はさらに手前に位置している。どのローカルファイルがビルドコンテキストに入る資格を持つかを最初に決めることで、`COPY` の内容、ビルドの効率、キャッシュの安定性に同時に影響を与える。

今回の実験を通じて、Dockerfile を単に順番に並んだいくつかのコマンドとしてではなく、入力と依存関係を持ち、中間結果を再利用できるビルドの過程として捉えるようになった。

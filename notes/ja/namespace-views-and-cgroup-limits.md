# Namespace は見え方を隔離し、Cgroup は使用量を制限する

[English](../namespace-views-and-cgroup-limits.md) | [中文](../zh/namespace-views-and-cgroup-limits.md) | **日本語**

Namespace を理解したあと、ひとつ疑問が湧いた。コンテナからはすでに外部のプロセス、ファイルシステム、ネットワーク環境が見えないのに、なぜ Cgroup まで必要なのか。

答えは、両者が解決している問題の種類がそもそも違う、ということである。

```text
Namespace  プロセスのグループが「どのリソースを見て、操作できるか」を決める
Cgroup     プロセスのグループが「リソースをどれだけ使えるか」を計測し、制限する
```

## Namespace が隔離するのはリソースのビュー

プロセスから見える PID、マウントツリー、ネットワークデバイス、ホスト名などは、もともと Linux カーネルがプロセスに提供している抽象的なビューである。Namespace は、プロセスごとに異なるビューを使わせる。

- PID Namespace により、コンテナからは自身の範囲内のプロセス番号だけが見える。
- Mount Namespace により、コンテナは独立したマウント関係を持つ。
- Network Namespace により、コンテナは独自のネットワークインターフェース、IP アドレス、ルーティングテーブルを持つ。

この隔離は、単に表示内容を変えているだけではない。たとえば Network Namespace ごとのルーティングテーブルや仮想ネットワークインターフェースは、カーネルが実際に別々に管理しているリソースのインスタンスである。とはいえ、それらはやはり同じ Linux カーネルによって管理されており、下層の CPU やメモリも同じ 1 台のマシンのものである。

そのため、あるコンテナからはホスト上のほかのプロセスが見えなくても、マシン全体のメモリを使い果たしたり、CPU を長時間占有したりすることはありうる。Namespace はこの問題を解決しない。

## Cgroup はプロセスのリソース勘定

Cgroup は Control Group の略である。プロセスをグループにまとめ、さまざまなコントローラーがそのプロセス群のリソースを計測・スケジューリング・制限する。

代表的なコントローラーは次のとおり。

| コントローラー | 役割 |
|---|---|
| `cpu` | CPU スケジューリングの重みや時間クォータを設定する |
| `memory` | メモリ使用量を計測し、制限する |
| `pids` | プロセスとスレッドの数を制限する |
| `io` | ブロックデバイスの I/O を計測し、制限する |
| `cpuset` | 使用できる CPU とメモリノードを指定する |

たとえば `memory.max=512M` は、専用のメモリ領域をあらかじめ切り出すという意味ではない。そのグループに属するプロセスのメモリ使用量の合計が、この上限を超えてはならないという意味である。Cgroup は、縮小版の仮想コンピューターというより、利用量の計測と予算ルールを備えた「リソースの勘定口座」に近い。

## Cgroup v2 は単一の統合ツリー

現代の Linux では主に Cgroup v2 が使われている。すべての Cgroup ノードは、1 本の統合された階層ツリーを構成する。

```text
/
├── system.slice
│   ├── docker.service
│   │   ├── container-a  ← あるコンテナのプロセス群
│   │   └── container-b  ← 別のコンテナのプロセス群
│   └── ssh.service
└── user.slice
    └── user-1000.slice
        └── shell        ← シェルプロセス
```

通常の Cgroup v2 のプロセスモデルでは、各プロセスはある時点でこのツリー内のただ 1 つの Cgroup ノードに属する。プロセスが子プロセスを作ると、子プロセスは最初は親の Cgroup を引き継ぐ。別のノードの `cgroup.procs` に PID を書き込むと、そのプロセス全体がそのノードへ移動する。

```bash
echo 1234 > /sys/fs/cgroup/service-b/cgroup.procs
```

プロセスが直接属するノードは 1 つだけだが、そのノードと祖先ノードすべてのルールから同時に制約を受ける。

```text
apps                 全アプリケーション合計で最大 4 GB
└── service-a        このサービスは最大 1 GB
    └── プロセス 1234
```

子ノードは制限をさらに厳しくすることしかできず、祖先がすでに設定した上限を超えることはできない。

親ノードのプロセスと子ノードが同じリソースを奪い合うことを避けるため、Cgroup v2 には通常のドメインコントローラーに関する構造上のルールもある。ルート以外のノードがコントローラーを子ノードへ委譲するには、原則として、まず自分のプロセスを子ノードへ移す必要がある。そのため実際の管理ツリーでは、プロセスをリーフノードに置き、中間ノードはリソースの整理と配分に使うのが一般的である。

## ノードは一部のコントローラーだけを有効にすればよい

コントローラーはカーネルが提供するリソース制御の機能であり、特定の Cgroup ノードに属するものではない。Cgroup ノードは、自分がどのコントローラーを使えるか、そしてどのコントローラーを子ノードへ引き継ぐかを決める。

混同しやすいファイルが 2 つある。

```text
cgroup.controllers       このノードで利用でき、子へ委譲しうるコントローラー
cgroup.subtree_control   このノードが直下の子ノードに対して実際に有効にしたコントローラー
```

たとえば、ルートノードが次のコントローラーをサポートしているとする。

```text
cpu memory pids io
```

それでも、下位に対しては一部だけを有効にできる。

```bash
echo "+cpu +memory" > /sys/fs/cgroup/cgroup.subtree_control
```

この場合、直下の子ノードは CPU とメモリの制御を設定できるが、委譲されていない `pids` と `io` のコントローラーは、自身のサブツリー内で使えない。リソース制御はトップダウンのルールに従う。親ノードが提供していないコントローラーを、子ノードが独自に有効にすることはできない。

したがって、次の 2 つは別物である。

```text
プロセスが Cgroup に属している
        ≠
すべてのリソースに具体的な上限が設定されている
```

あるプロセスが `/app/service` に属していても、経路上のどこにも `memory.max` が設定されていなければ、その Cgroup ツリーによるメモリのハードリミットは存在しない。

## `/proc/self/cgroup` が示すもの

現在のプロセスが属する Cgroup は、次のように確認できる。

```bash
cat /proc/self/cgroup
```

私の実験環境では、次のように表示された。

```text
0::/.lxc
```

各行の形式は次のとおり。

```text
階層 ID : コントローラーの一覧 : Cgroup のパス
```

Cgroup v2 では、すべてのコントローラーが統合された単一の階層を使うため、通常は次のように表示される。

```text
0::<path>
```

`0` は統合階層を表し、中央のフィールドには個別のコントローラーが列挙されなくなっている。`/.lxc` は、現在の Cgroup Namespace から見たパスである。外側のホストから見た完全なパスは、これより長い場合がある。

Cgroup v1 ではコントローラーごとに別々の階層を作れるため、1 つのプロセスが `/proc/self/cgroup` に複数行表示され、CPU やメモリなどの階層ごとに異なるパスを持つことがある。これらのコントローラーを 1 本のツリーに統合したのが、まさに Cgroup v2 である。

## Docker は Cgroup をどう使うか

Docker はコンテナを作成するとき、コンテナのプロセスを対応する Cgroup に入れ、起動オプションをカーネルのリソースルールに変換する。

```bash
docker run \
    --memory=512m \
    --cpus=0.5 \
    --pids-limit=100 \
    nginx
```

Cgroup v2 では、おおよそ次のように対応する。

```text
Docker のオプション   Cgroup の制御インターフェース
--memory=512m   →    memory.max
--cpus=0.5      →    cpu.max
--pids-limit    →    pids.max
```

Docker は CPU スケジューリングやメモリ制限を独自に実装し直しているわけではない。コンテナのプロセスを整理したうえで、Linux カーネルに既存の Cgroup の仕組みを設定しているのである。

## 現時点での理解

Namespace と Cgroup は、次のように区別できる。

```text
Namespace  プロセスから見えるリソースのビューを隔離・仮想化する
Cgroup     プロセスグループの実際のリソース使用量を計測・スケジューリングし、上限を課す
```

両者を組み合わせることで、コンテナ内のプロセスは独立した環境にいるかのように振る舞いつつ、ホストのリソースを際限なく消費することはできなくなる。それでも、それらは同じ Linux カーネルが管理する普通のプロセスにすぎない。

もう 1 つ、境界線として押さえておくべき点がある。Namespace と Cgroup だけで完全なセキュリティモデルになるわけではない。コンテナでは通常、rootfs、Capabilities、Seccomp などの仕組みも組み合わせて、プロセスがアクセスできるファイルや実行できる操作をさらに制限している。

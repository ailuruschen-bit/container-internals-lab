# Linux コンテナネットワークの仕組み：Network Namespace から NAT まで

[English](../linux-container-networking.md) | [中文](../zh/linux-container-networking.md) | **日本語**

コンテナのネットワークは、一見すると独立した小さなネットワークのように見える。コンテナは自分専用のネットワークインターフェース、IP アドレス、ルート、ポートを持ち、ほかのコンテナやインターネットとも通信できる。

Docker は TCP/IP プロトコルスタックを独自に実装し直しているわけではない。主に行っているのは、Network Namespace、veth、ブリッジ、ルーティング、Netfilter といった、Linux カーネルに既存の仕組みを組み合わせることである。

## 1. Network Namespace：独立したネットワーク環境

同じ Linux カーネルが管理するプロセスが、なぜ異なるネットワーク環境を持てるのか。

Network Namespace（NetNS）は、ネットワークに関わる一連のカーネルリソースを隔離する。対象には次のものが含まれる。

- ネットワークインターフェースと IP アドレス
- IPv4 / IPv6 プロトコルスタック
- ルーティングテーブル
- ファイアウォールルール
- ソケットが使うポート空間
- `/proc/net`、`/sys/class/net` などのネットワーク関連のビュー

そのため、2 つのプロセスがそれぞれ自分の NetNS で `0.0.0.0:80` を待ち受けても、ポートが同じであることによる衝突は起きない。

NetNS は、1 台のコンピューターが持つ独立したネットワークコンテキストにたとえられる。ただし、NetNS を新規作成して得られるのは隔離されたネットワーク環境だけであり、外部への接続性が自動的に備わるわけではない。作成直後は通常ループバックインターフェース `lo` しかなく、ネットワークインターフェース、IP アドレス、ルートを別途設定する必要がある。

## 2. veth ペア：ネットワーク環境同士をつなぐ仮想ケーブル

異なる NetNS のネットワークリソースが互いに隔離されているなら、それらはどのように接続されるのか。

veth ペアは、互いにつながった 1 組の仮想イーサネットインターフェースである。一方の端から送信されたデータは、カーネルによってもう一方の端で受信される。

```text
NetNS A                         NetNS B
  veth-a  ◄──────────────────►  veth-b
```

両端はそれぞれ別の NetNS に配置できる。データの転送はすべて Linux カーネル内で完結し、物理 NIC を経由しない。

「仮想ケーブル」というたとえは直感的だが、より正確には、veth ペアはケーブルの両端にある仮想ネットワークインターフェースまで含んだものと捉えるべきである。各端は、それぞれ独自のインターフェース名、MAC アドレス、統計情報を持つ。

Docker は通常、一方の端をコンテナの NetNS に移してコンテナ内で `eth0` という名前を付け、もう一方の端をホストの NetNS に残して Linux ブリッジに接続する。

## 3. Linux ブリッジ：複数のコンテナをつなぐ仮想スイッチ

1 組の veth で接続できるのは 2 つの端点だけである。複数のコンテナを同じネットワークに参加させるには、多数のインターフェースを接続できるデバイスが必要になる。

Linux ブリッジは、カーネルが実装する仮想的な L2 スイッチである。ホスト側の複数の veth インターフェースを、同じブリッジに接続できる。

```text
Container A                     Container B
  eth0                            eth0
    │                              │
  veth                            veth
    └──────── Linux Bridge ─────────┘
```

ブリッジはフレームの送信元 MAC アドレスを学習し、宛先 MAC アドレスに基づいてどのポートから転送するかを決める。宛先が未知の場合やブロードキャストの場合は、ほかの適切なポートへ転送する。

2 つのコンテナが同じブリッジネットワーク上にあり、IP アドレスとサブネットが正しく設定されていれば、通常は NAT を介さずにブリッジ経由で直接通信できる。

```text
Container A
    → veth
    → Linux Bridge
    → veth
    → Container B
```

ブリッジ自体は L2 で動作するが、ホストは通常ブリッジのインターフェースにも IP アドレスを割り当てる。この IP アドレスはコンテナのデフォルトルートにおけるゲートウェイとなり、トラフィックをコンテナネットワークからホストの L3 ルーティングへ渡す役割を果たす。

## 4. ルーティングと NAT：コンテナが外部ネットワークにアクセスする仕組み

コンテナが使う内部 IP アドレスは、通常、外部ネットワークから直接ルーティングできない。Docker のブリッジネットワークでよく使われるデフォルトの `nat` モードでは、ホストがゲートウェイとアドレス変換の役割を担う。

コンテナがインターネットへパケットを送るとき、経路はおおよそ次のようになる。

```text
コンテナの eth0
    → veth ペア
    → Linux ブリッジ
    → ホストの IP ルーティング
    → Netfilter MASQUERADE / SNAT
    → ホストの外部 NIC
    → インターネット
```

ここでは 2 種類の機能が必要になる。

1. **ルーティングによる転送**：ホストがパケットをコンテナ用ブリッジから外部インターフェースへ転送する。
2. **送信元アドレス変換**：コンテナの内部の送信元アドレスを、ホストが外部向けに使うアドレスに書き換える。必要に応じて送信元ポートも書き換える。

ホストの外部アドレスが変わる可能性がある場合は、通常 MASQUERADE が使われる。これは、出口インターフェースのアドレスを自動的に選ぶ SNAT の一種と理解できる。

Netfilter のコネクショントラッキング機構である conntrack は、接続とアドレス変換の状態を記録する。外部からの応答が戻ってくると、カーネルはこの状態をもとに元の宛先情報を復元し、パケットを正しいコンテナへルーティングする。こうして複数のコンテナが、ホストの外部向け IP アドレスを共有できる。

NAT はコンテナのネットワーク接続に必須の条件ではない。外部ネットワークがコンテナのネットワークセグメントへのルーティング方法をすでに知っていれば、直接ルーティングを使うこともできる。Docker のブリッジネットワークは `routed` などのゲートウェイモードもサポートしている。ここで扱っているのは、最も一般的なデフォルトの NAT モデルである。

## 5. ポートマッピング：外部からコンテナのサービスへのアクセスを許可する

アウトバウンドの NAT が主に解決するのは、コンテナ側から接続を開始する場合の問題である。では、ホストのアドレスしか知らない外部のクライアントは、どのようにしてコンテナ内のサービスに接続を開始できるのか。

Docker のポート公開は、ホストのアドレスとコンテナのアドレスの間に、あらかじめ転送関係を設定する。

```bash
docker run -p 8080:80 nginx
```

これは、ホストの `8080` 番ポートをコンテナの `80` 番ポートに公開することを意味する。Linux 上のデフォルトの NAT モードでは、典型的なインバウンドの経路は次のとおりである。

```text
クライアント
    → ホストの IP:8080
    → Netfilter DNAT
    → コンテナの IP:80
    → Linux ブリッジ
    → veth ペア
    → コンテナ内のサービス
```

DNAT はインバウンドパケットの宛先アドレスとポートを書き換え、転送ルールがパケットの通過を許可し、conntrack が応答を正しい逆変換の経路で返す。アクセス元や Docker の設定によっては、実際の実装に追加の Netfilter ルールやユーザーランドプロキシが関わることもある。

ポートマッピングと conntrack は役割が異なる。

- ポートマッピングは、「ホストのどのポートをどのコンテナのサービスへ転送するか」をあらかじめ定義する。
- conntrack は、実際の個々の接続とその変換状態を動的に記録する。

`-p` でホストの IP を指定しなかった場合、ポートは通常ホストのすべてのアドレスにバインドされる。外部から実際にアクセスできるかどうかは、ホストのファイアウォール、ルーティング、クラウドプラットフォームのセキュリティルールにも左右される。

## 6. Docker はこれらの仕組みをどう組み合わせるか

典型的な Linux ブリッジネットワークは、次のように図示できる。

```text
                         Internet
                            │
                ホストの外部ネットワークインターフェース
                            │
                  IP Routing / Netfilter NAT
                            │
             Linux Bridge（例：docker0）
                     /               \
               host veth          host veth
                   │                  │
               veth Pair          veth Pair
                   │                  │
          Container A NetNS   Container B NetNS
             eth0                 eth0
          172.17.0.2           172.17.0.3
```

典型的な 3 つの通信シナリオは、次のように整理できる。

| シナリオ | 主な仕組み |
|---|---|
| コンテナ A → コンテナ B | veth ペア + Linux ブリッジ |
| コンテナ A → インターネット | veth ペア + ブリッジ + ルーティング + MASQUERADE/SNAT |
| インターネット → コンテナ A のサービス | ポートマッピング + DNAT + ルーティング + ブリッジ + veth ペア |

それぞれの仕組みは、次の 3 つの問いに答えている。

```text
隔離された NetNS をどう外へつなぐか？           → veth ペア
複数のコンテナをどう同じネットワークにつなぐか？ → Linux ブリッジ
内部アドレスからどう外部にアクセスし、
外部からどうアクセスされるか？                   → ルーティング、NAT、ポート公開
```

macOS 上の Docker Desktop では、コンテナとこれらの Linux ネットワークの仕組みは、隠された Linux 仮想マシンの中で動作している。macOS から仮想マシン、さらにコンテナへのポートアクセスは、Docker Desktop が提供する転送レイヤーも経由する。そのため、macOS をネイティブな Linux の Docker ホストと同じように扱って、すべてのインターフェースや Netfilter ルールを直接観察することはできない。

## 7. AWS VPC ネットワークとの関係

Linux のコンテナネットワークと AWS VPC は実装のレイヤーが異なるが、それぞれが解決する問題を通じて関連づけることができる。

| AWS のコンポーネント | 主な役割 |
|---|---|
| NAT ゲートウェイ | プライベートサブネット内のリソースから外部の IPv4 ネットワークへ接続を開始し、対応する応答を受け取れるようにする |
| インターネットゲートウェイ | VPC のルートテーブルにおけるインターネット向けのターゲット。アドレスとルーティングの条件を満たせばパブリックな通信を可能にする |
| ALB / NLB | リスナーでインバウンド接続を受け付け、ターゲットグループ内のバックエンドサービスへトラフィックを分散する |
| インターフェイスエンドポイント | PrivateLink とサブネット内のプライベート IP を通じて、対応するサービスにアクセスする |
| ゲートウェイエンドポイント | ルートテーブルを通じて S3、DynamoDB にプライベートにアクセスする |

### NAT ゲートウェイと Docker のアウトバウンド NAT

どちらも「内部のプライベートアドレスから外部ネットワークへ接続を開始する」という問題を解決し、応答トラフィックが戻ってくることを許可する。ただし、AWS の NAT ゲートウェイはクラウドプラットフォームが運用するマネージドなネットワークサービスであり、Docker が 1 台の Linux ホスト上に設定する Netfilter ルールとは別物である。

NAT ゲートウェイは、インターネットからの任意のインバウンドのポート転送を提供しない。サービスを公開する必要がある場合、AWS では通常、パブリックアドレスを持つリソースや、ALB、NLB などのエントリーポイントを使う。

### インターネットゲートウェイは単独で効くスイッチではない

インターネットゲートウェイを VPC にアタッチしても、すべてのインスタンスがすぐにインターネットへアクセスできるようになるわけではない。正しいルートテーブルが必要であり、IPv4 の場合、インスタンスには通常パブリック IPv4 アドレスか Elastic IP アドレスも必要になる。さらに、セキュリティグループとネットワーク ACL が該当するトラフィックを許可していなければならない。

### VPC エンドポイントとポートマッピング

インターフェイスエンドポイントは、サービスをパブリックに公開する入口ではない。サブネット内の Elastic Network Interface とプライベート IP を通じて、VPC 内のクライアントが AWS のサービスや PrivateLink 対応のサービスにプライベートにアクセスできるようにするものである。

一方、ゲートウェイエンドポイントは、ルートテーブルによって S3、DynamoDB 宛てのトラフィックをエンドポイントへ誘導する。どちらの VPC エンドポイントも、パブリックな入口や NAT を経由しないようにするためのものであり、「ホストのポートをコンテナのポートへ転送する」ポートマッピングとは異なる仕組みである。

## 現時点での理解

Linux のコンテナネットワークは、カーネルの仮想デバイスとネットワーク機能を組み合わせて作られたインフラストラクチャである。

```text
Network Namespace  ≈ 独立したネットワークコンテキスト
veth Pair          ≈ 仮想ケーブルとその両端のインターフェース
Linux Bridge       ≈ L2 スイッチ
Routing + NAT      ≈ ゲートウェイによるルーティングとアドレス変換
Port Mapping       ≈ 事前に設定されたインバウンドのポート転送
```

コンテナは、物理 NIC を占有することも、専用の Linux カーネルを持つこともなく、独立した IP アドレス、ルート、ポート空間を持つことができる。Docker の役割は、これらの Linux の仕組みを、コンテナのライフサイクルに合わせて自動的に作成・接続・設定・回収することである。

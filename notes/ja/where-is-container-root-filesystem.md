# Linux のファイルシステム、マウント、Mount Namespace について学んだこと

[English](../where-is-container-root-filesystem.md) | [中文](../zh/where-is-container-root-filesystem.md) | **日本語**

## 1. Linux のディレクトリツリーを捉え直す

Windows のエクスプローラーのようなグラフィカルな見方に慣れていると、「OS には固定されたディレクトリツリーが 1 つあり、すべてのプロセスがその中でファイルにアクセスし、操作している」と考えがちである。

しかし、Linux の実際のモデルはそうではない。

- ルートディレクトリ `/` は、特定の物理ディスクと同じものではない。
- 1 つの完全なディレクトリツリーは、複数のファイルシステムを組み合わせて構成できる。
- プロセスごとに、見えているディレクトリツリーが同じとは限らない。
- ディスク上の実データに対応するディレクトリもあれば、内容をカーネルが動的に提供するディレクトリもある。

例を挙げる。

```text
/
├── etc/      通常のファイルシステム
├── home/     通常のファイルシステム
├── proc/     procfs（仮想ファイルシステム）
└── sys/      sysfs（仮想ファイルシステム）
```

つまり、Linux のディレクトリツリーは、カーネルがファイルシステムとマウントの仕組みによって組み立てた論理的なビューであり、物理的に固定された 1 本のツリーではない。

## 2. マウントと Mount Namespace

### マウント（Mount）

マウントとは、あるファイルシステムを既存のディレクトリツリーの特定の位置に接続することである。

例：

```bash
mount /dev/sdb1 /data
```

このコマンドは、`/dev/sdb1` 上のファイルシステムを `/data` にマウントする。以降、`/data` にアクセスすると、カーネルはこのマウント関係に従って対応するファイルシステムへ入っていく。

マウントはファイルの中身をコピーしない。ディレクトリツリー上のパスとファイルシステムとの対応関係を作るだけである。

### Mount Namespace（マウント名前空間）

Mount Namespace は、一群のプロセスが共有する「マウント関係のビュー」と考えることができる。

Linux ホスト上の通常のプロセスは、たいてい初期の Mount Namespace に属している。一方、コンテナのプロセスは独立した Mount Namespace を使うことができる。

```text
Namespace A          Namespace B
    /                     /
    └── data/             └── data/
         │                     │
 ファイルシステム X     ファイルシステム Y
```

2 つのプロセスが同じ `/data` というパスにアクセスしても、それぞれ別のファイルシステムに到達しうる。

注意すべき点：

- Namespace は、下層のファイルシステムを自動的にコピーするわけではない。
- Namespace は、プロセスのルートディレクトリを自動的に変更するわけではない。
- 異なる Namespace が、同じ下層のファイルリソースを参照することもできる。
- マウントイベントがほかの Namespace に伝播するかどうかは、`shared` や `private` といったマウント伝播（propagation）の属性にも左右される。

## 3. プロセスの `root` と `cwd`

Linux カーネルは、プロセスごとに 2 つの重要なファイルシステムコンテキスト属性を管理している。

- `root`：絶対パスを解決する際の起点。
- `cwd`：相対パスを解決する際の起点。

どちらも通常は親プロセスから継承される。

例：

```bash
cd /home/user
```

これはシェルプロセスの `cwd` を変更する。

一方、次のシステムコールはプロセスの `root` を `/some/rootfs` に変更し、以降の絶対パスの解決がそこから始まるようにする。

```c
chroot("/some/rootfs");
```

`chroot` が変えるのはパス解決の起点だけであり、それ自体は完全なセキュリティ隔離の仕組みではない。コンテナランタイムは、Mount Namespace、マウント設定、権限の制限、`pivot_root` などの仕組みを組み合わせてコンテナの環境を用意する。

したがって、次の 3 つの独立した概念を区別する必要がある。

```text
root             絶対パス解決の起点
cwd              相対パス解決の起点
Mount Namespace  見えているファイルシステムのマウント関係
```

同じ Mount Namespace に属する 2 つのプロセスでも、`root` と `cwd` が異なることはありうる。逆に、2 つのプロセスがどちらも自分のルートディレクトリを `/` と呼んでいても、見えているファイルシステムの内容が異なることもある。

## 4. OverlayFS と Docker コンテナのルートディレクトリ

Overlay とは「重ねる」「覆いかぶせる」という意味である。OverlayFS は、複数のディレクトリ層を 1 つに統合したファイルシステムのビューを作る。

主な構成要素は次のとおり。

- `lowerdir`：1 つ以上のベース層。通常は読み取り専用の層として使われる。
- `upperdir`：書き込み可能な層。新規作成や変更されたファイルを保存する。
- `workdir`：OverlayFS の内部処理に必要な作業用ディレクトリ。
- `merged`：マウント完了後に利用者へ提示される統合ビュー。

```text
lowerdir ──┐
           ├── OverlayFS ── merged ── コンテナの /
upperdir ──┘
```

ファイルを探すとき、OverlayFS はまず `upperdir` を、次に `lowerdir` を確認する。上下の層に同名のディレクトリがある場合は、それらがマージされて見えることもある。

`lowerdir` にしか存在しないファイルをコンテナが変更する場合、OverlayFS は通常、まずそのファイルを `upperdir` にコピーし、上層のコピーを変更する。これが Copy-on-Write（コピーオンライト）である。

Docker コンテナは通常それぞれ専用の書き込み可能層を持つ。そのため、複数のコンテナがイメージのベース層を共有しつつ、各自の変更を互いに隔離できる。コンテナのプロセスに見えるのは OverlayFS が統合したディレクトリツリーであり、あるファイルが実際にどの層から来ているかを意識する必要はない。

また、コンテナ内の `/proc` は、カーネルの状態を丸ごとコピーしたものではない。コンテナランタイムがコンテナのマウントビューに procfs をマウントし、同じ Linux カーネルが、その procfs に対応する PID Namespace に基づいてプロセス情報を提示している。

そのため、コンテナ内のプロセスは自分を PID 1 として認識できる一方、ホスト側では同じプロセスを別の PID で識別している。どちらもカーネルが管理する同一のプロセスオブジェクトを読んでおり、見えている PID とプロセスの範囲が異なるだけである。

## 5. 最終的なメンタルモデル

Linux カーネルは、下層のファイルシステムリソースと、それらをディレクトリツリーに接続するマウント関係を管理している。各プロセスは、自身のファイルシステムコンテキストを通じてパスを解決する。

```text
Linux カーネル
    │
    ├── 下層のファイルシステムリソース
    │     ├── ext4
    │     ├── OverlayFS
    │     ├── procfs
    │     └── sysfs
    │
    └── Mount Namespace
          │
          ├── マウント関係のビュー A
          │      └── プロセス A（root / cwd）
          │
          └── マウント関係のビュー B
                 └── プロセス B（root / cwd）
```

要点：

1. ディレクトリツリーは、すべてのプロセスが共有しなければならない固定的な物理ツリーではない。
2. マウントは、ファイルシステムとディレクトリツリーとの接続関係を作る。
3. Mount Namespace は、プロセスのグループごとに異なるマウント関係のビューを与える。
4. `root` と `cwd` は、プロセスがパスを解決する起点を決める。
5. Docker は、Mount Namespace、ルートディレクトリの切り替え、OverlayFS などの仕組みを組み合わせ、コンテナのプロセスに独立したファイルシステム環境を提供している。

**コンテナのファイルシステム隔離の本質は、コンピューターを 1 台丸ごと複製することではない。同じ 1 つの Linux カーネルが、プロセスのグループごとに異なるファイルシステムのビューを組み立てていることにある。**

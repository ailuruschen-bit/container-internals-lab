# Docker のトラブルシューティング実践（2）：コンテナは動いているのにサービスが落ちている

[English](../19-docker-troubleshooting-service-down.md) | [中文](../zh/19-docker-troubleshooting-service-down.md) | **日本語**

前回見たのはコンテナが終了する場面だった。今回は、`docker ps` ではコンテナが `Up` のままなのに、サービスが応答しなくなっている。コンテナのメインプロセスが生きている限り、Docker は `Up` と表示し続ける。次に確認すべきなのは、サービスのプロセスがまだ存在しているかどうか、そして問題が起きる前にどのようなログを残したかである。

## 1. 状態と直近のログから調べる

まず `docker ps` でコンテナ名または ID を確認する。`compose.yaml` があるディレクトリで `docker compose ps` を実行すると、現在のプロジェクトで実行中のコンテナだけが一覧に表示される。同じプロジェクトですでに終了したコンテナも見たい場合は、`-a` を付ける。

| やりたいこと | コンテナ名または ID で指定 | Compose のサービス名で指定 |
|---|---|---|
| 直近 20 行を表示し、新しいログを追い続ける | `docker logs -f --tail=20 <container>` | `docker compose logs -f --tail=20 <service>` |
| プロセスを直接確認する | `docker top <container>` | `docker compose top <service>` |
| 対話型のシェルを開く | `docker exec -it <container> sh` | `docker compose exec <service> sh` |

サービスのコンテナが 1 つだけなら、どちらの列のコマンドでも通常は同じ調査ができる。たとえば `app` は Compose のサービス名で、`05-compose-app-1` はコンテナ名である。サービスに複数のレプリカがある場合、Compose の `logs` と `top` は複数のレプリカをまとめて確認でき、`exec` は `--index` で 1 つを選べる。

私はたいてい、まず直近の 20 行を確認してから、失敗したリクエストをもう一度送り、新しいエラーが出るかどうかを見る。`Ctrl+C` を押すとログの追跡が終わるが、コンテナは動き続ける。

## 2. サービスのプロセスがまだ存在するかを確認する

プロセスの一覧だけを確認したいときは、まず `docker top` を使う。これはコンテナの外からプロセスを一覧表示する。設定ファイル、権限、起動引数も確認したい場合は、`docker exec -it <container> sh` でコンテナに入り、`ps` を実行する。そのためには、イメージに `sh` と `ps` が含まれている必要がある。

起動スクリプトなどのプロセスしか残っておらず、想定していたサービスのプロセスがなくなっている場合は、ログに戻ってなぜ終了したのかを調べる。サービスのプロセスがまだ存在する場合は、コンテナの内側からサービスの待ち受けポートにリクエストを送り、サービス自体が応答できないのか、それともコンテナの外からのアクセスだけが失敗しているのかを切り分ける。

## 3. 修正をプロジェクトに書き戻す

コンテナに入って一時的に設定を変え、仮説を検証するのは構わない。しかし、その変更が現在のコンテナの書き込み可能層にしか残っていなければ、コンテナを作り直したときに失われる。原因を確認できたら、修正を `compose.yaml`、ホスト上のマウントされた設定ファイル、あるいはアプリケーションのソースコードに書き戻す。どこを直すかは、障害の原因がどこにあるかによる。

たとえば、`compose.yaml` で `app` の環境変数を修正した後は、プロジェクトのディレクトリで次を実行する。

```bash
docker compose up -d app
docker compose ps
docker compose logs --tail=20 app
```

`up` は設定の変更に応じてコンテナを作り直す。`docker compose restart app` だけを実行しても既存のコンテナが再起動されるだけで、作成時の環境変数などの設定がそのまま使われる。修正にイメージの再ビルドが必要な場合は、`docker compose up -d --build app` を使う。最後に、元々失敗していた API にもう一度リクエストを送り、サービスが本当に復旧したことを確認する。

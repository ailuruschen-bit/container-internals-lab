# Docker の `USER`：アプリケーションを非 root で実行する

[English](../15-docker-user-best-practices.md) | [中文](../zh/15-docker-user-best-practices.md) | **日本語**

今日は Dockerfile の `USER` に関するセキュリティのプラクティスを学んだ。これが解決する問題は単純である。アプリケーションが通常の動作に管理者権限を必要としないなら、コンテナのメインプロセスをデフォルトで root として実行すべきではない。

ただし、「コンテナ内の root はホストの root と同じ」というのは正確ではない。コンテナは引き続き、Namespace、Capability、Seccomp、マウントの範囲などの仕組みによって制限されている。非 root ユーザーを使う意味は、アプリケーションが侵害されたときの権限の範囲をさらに狭め、コンテナに多層防御の層を 1 つ加えることにある。

## 1. `USER` を書かないとどうなるか

ベースイメージにも Dockerfile にもほかのユーザーが指定されていなければ、コンテナのプロセスは通常デフォルトで root を使う。

以前ビルドした Spring Boot のイメージを確認する。

```bash
docker image inspect spring-lab:v2 \
  -f '{{json .Config.User}}'
```

手元の結果は空文字列だった。

```text
""
```

これはイメージがデフォルトのユーザーを明示的に設定しておらず、実行時に root が使われることを意味している。直接確認することもできる。

```bash
docker run --rm \
  --entrypoint id \
  spring-lab:v2
```

出力に `uid=0(root)` が含まれていれば、コンテナのプロセスは root として動いている。

## 2. コンテナ内の root がすぐにホストの全権限を得るわけではない

UID が 0 であっても、Docker はデフォルトで Linux の root が持つすべての Capability をコンテナに与えるわけではなく、コンテナから見えるファイルシステムやプロセスのビューも隔離されている。そのため、アプリケーションの脆弱性が悪用されても、攻撃者は「コンテナ内で root である」というだけで自動的にホストの root になるわけではない。

それでも、コンテナ内の root はより大きな破壊力を持っている。たとえば次のようなことである。

- コンテナ内の、本来 root だけがアクセスできる設定やファイルを読み取ったり変更したりする。
- アプリケーションのプロセスの改ざん、追加のプログラムの起動、ファイルの権限の変更がしやすくなる。
- コンテナにマウントされたディレクトリに、より大きな影響を与える。
- 追加の Capability、特権モード、カーネルの脆弱性が存在する場合に、リスクを増幅させる。

コンテナがさらに Docker のソケットやホストの機密性の高いパスをマウントしていたり、`--privileged` などの高い権限の設定を使っていたりすれば、リスクはいっそう高まる。

したがって、非 root ユーザーを使うのは、それがコンテナのあらゆる隔離の代わりになるからではなく、最小権限の原則に従うためである。アプリケーションには、仕事をこなすのに本当に必要な権限だけを与える。

## 3. `USER` が実際に影響する段階

基本的な構文は次のとおりである。

```dockerfile
USER <user>
USER <user>:<group>
USER <UID>:<GID>
```

`USER` は、現在のステージで以降の命令が使うデフォルトのユーザーを設定する。対象は次のとおりである。

- 以降の `RUN` によるビルド手順。
- コンテナ実行時の `ENTRYPOINT`。
- コンテナ実行時の `CMD`。

例：

```dockerfile
USER app:app

RUN whoami
ENTRYPOINT ["java", "-jar", "app.jar"]
```

ここでの `RUN whoami` はビルドの段階ですでに `app` として実行され、最終的な Java のプロセスもデフォルトで `app` として動く。

そのため、`USER` を Dockerfile の先頭に安易に置くことはできない。切り替えた後にソフトウェアのインストール、システムディレクトリの作成、root のファイルの変更を行うと、通常は権限不足で失敗する。

## 4. 推奨される順序：特権の必要な操作を先に済ませ、最後に権限を下げる

より明確な Dockerfile の順序は次のとおりである。

```text
root としてビルドステージを開始する
    ↓
ソフトウェアのインストール、ユーザーとグループの作成
    ↓
ディレクトリの作成と所有権の設定
    ↓
アプリケーションのファイルのコピー
    ↓
USER で一般ユーザーに切り替える
    ↓
ENTRYPOINT / CMD でアプリケーションを起動する
```

先に一般ユーザーに切り替えておき、権限が必要になるたびに root に戻すのではない。前のほうでまとめて行える特権の必要な操作はできるだけ一度に済ませ、Dockerfile の最後の実行時の身元を非 root のままにしておくべきである。

後続のビルド手順で本当に一時的な切り替えが必要な場合は、明示的に次のように書ける。

```dockerfile
USER root
RUN some-privileged-build-step
USER app:app
```

ただし、コンテナのデフォルトの実行時の身元を決めるのは、最終ステージで最後に有効になっている `USER` である。root に戻した後、権限を下げ直すのを忘れてはいけない。

## 5. Java の実行ステージでユーザーを作成する

以前の Maven のマルチステージビルドでは、ユーザーは最終の JRE のステージで作成すべきである。

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build

WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests


FROM eclipse-temurin:21-jre

RUN groupadd --gid 10001 app && \
    useradd --uid 10001 \
            --gid 10001 \
            --no-create-home \
            app

WORKDIR /app

COPY --from=build \
     --chown=10001:10001 \
     /build/target/*.jar \
     app.jar

USER 10001:10001

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

重要な点がいくつかある。

1. `groupadd` と `useradd` は root として実行する。
2. ユーザーは、Maven のビルダーのステージだけでなく、最終の JRE のステージで作成する。
3. `COPY --chown` で、JAR をコピーするときにファイルの所有者を直接設定する。
4. `USER` は、root 権限が必要な手順の後に置く。
5. Java のプロセスは、最終的に UID/GID `10001:10001` として動く。

ユーザーを作成するコマンドは、ベースイメージによって異なることがある。たとえば Alpine ではよく `addgroup` と `adduser` を使い、Debian 系や Ubuntu 系のイメージではよく `groupadd` と `useradd` を使う。コマンドをすべてのベースイメージにそのまま機械的に当てはめることはできない。

## 6. なぜ UID と GID を明示的に指定するのか

システムに ID を自動で割り当てさせると、ビルド結果によって UID/GID が異なる可能性がある。コンテナがイメージ内部のファイルにしかアクセスしないうちは影響は目立たないが、ボリュームやホストのディレクトリをマウントすると、カーネルが実際に権限を判定するのに使うのは数値の UID/GID である。

たとえば次のように明示的に使うと、

```text
UID 10001
GID 10001
```

ファイルの所有権がより安定し、デプロイ先の環境のストレージの権限とも調整しやすくなる。

具体的な数値に統一された決まりはないが、ベースイメージの中でまだ使われていない UID/GID を選び、チームやデプロイ先の環境で取り決めを一貫させるべきである。

`USER app:app` のほうが読みやすく、`USER 10001:10001` はコマンドの実行時に名前からユーザーを解決し直すことに依存しない。どちらの方法でもよく、重要なのはイメージ内のユーザー、グループ、ファイルの権限が一貫していることである。

## 7. `user:group` の意味

```dockerfile
USER app:app
```

コロンの前がユーザー、後ろがデフォルトのグループである。数値を使うこともできる。

```dockerfile
USER 10001:10001
```

グループを明示的に指定すると、プロセスはそのグループを使い、Dockerfile の `USER` は、そのユーザーに設定されたほかの補助グループを自動的には保持しない。アプリケーションが本当に追加のグループの権限を必要とするなら、`/etc/group` に列挙されたすべての補助グループが自動的に有効になると仮定するのではなく、実行時の設定で明示的に扱うべきである。

## 8. 非 root ユーザーは必要な権限を実際に持っていなければならない

`USER app` を 1 行追加するだけで、ファイルの権限が自動的に直るわけではない。アプリケーションが JAR を読み込んだり、ログを書いたり、一時ファイルを作ったりする必要があるなら、対応するディレクトリがそのユーザーのアクセスを許可していなければならない。

たとえば、アプリケーションが `/app/data` に書き込む必要がある場合：

```dockerfile
RUN mkdir -p /app/data && \
    chown -R 10001:10001 /app/data

USER 10001:10001
```

ボリュームやバインドマウントをマウントすると、マウントされた内容がイメージのそのパスにあった元のファイルのビューを覆い隠し、その UID/GID も実際のストレージに由来する。Dockerfile の中ですでに `chown` していても、実行時にマウントされたディレクトリでは、所有権の不一致によって `Permission denied` が発生することがある。

したがって、非 root に切り替えた後によくある問題は、プログラムそのものではなく、次のようなものであることが多い。

- アプリケーションのディレクトリがまだ root の所有になっている。
- ログ、キャッシュ、アップロードのディレクトリに書き込めない。
- マウントしたストレージの UID/GID がコンテナのユーザーと一致しない。
- プログラムが root でなければ実行できない操作に依存している。

正しいやり方は、アプリケーションに必要なディレクトリの権限だけを与えることであり、エラーを回避するためにコンテナ全体を root に戻すことではない。

## 9. 実行時にも `USER` を上書きできる

Dockerfile の `USER` は安全なデフォルト値であり、上書きできない強制的なポリシーではない。

`docker run` では次のように指定できる。

```bash
docker run --rm \
  --user 10001:10001 \
  my-app:v1
```

Compose での対応する書き方：

```yaml
services:
  app:
    image: my-app:v1
    user: "10001:10001"
```

実行する側が `--user 0` を明示してイメージのデフォルト値を上書きする可能性もある。したがって、Dockerfile の `USER` の価値は、安全な使い方をデフォルトの振る舞いにすることにある。より厳しい制限には、デプロイ先のプラットフォームのポリシー、Capability の制御、読み取り専用のファイルシステム、危険なマウントを避けることなどの仕組みを組み合わせる必要がある。

## 10. 現時点での理解

`USER` についての現在の理解は、次のようにまとめられる。

```text
root は実行環境の準備だけを担う
    ├── 依存関係のインストール
    ├── ユーザーとグループの作成
    ├── ディレクトリの作成
    └── ファイルの権限の設定
            │
            ▼
USER app:app
            │
            ▼
一般ユーザーがアプリケーションを実行する
```

非 root ユーザーを使っても、コンテナが絶対に安全になるとは保証できないし、コンテナ内の root をホストの root と単純に同一視することもできない。それが本当に解決するのは、アプリケーション自体が悪用されたとき、攻撃者がまず手にするのが、コンテナ内のすべてのファイルにアクセスでき、許可されたすべての特権操作を実行できる root ではなく、権限の限られたプロセスの身元にすぎない、ということである。

最も実用的な原則は次のとおりである。**アプリケーションが root を必要としないなら、最終の実行ステージで明示的にユーザーを作成し、必要なディレクトリの権限を整え、`USER` をアプリケーションの起動前の最後の設定の 1 つにすること。**

# OS はどのように CPU を「取り戻す」のか

[中文](../how-the-kernel-takes-back-the-cpu.md) | [English](../en/how-the-kernel-takes-back-the-cpu.md) | **日本語**

1 つの CPU コアが同時に実行できる命令の流れは 1 つだけである。あるプロセスが CPU を占有し続ければ、ほかのプロセスには実行の機会が回ってこない。OS には、必要なときに制御を取り戻し、次にどのプロセスを実行するかを決める仕組みが欠かせない。

## 通常のジャンプだけでは、OS は CPU を取り戻せない

CPU は、自分がどの「プロセス」を実行しているかを知らない。現在のレジスタ状態のもとで、PC（プログラムカウンタ）が指す命令を取り出しては実行することを繰り返しているだけである。

プログラムはジャンプ、関数呼び出し、リターンといった命令で PC を書き換えられるが、これらはあくまで実行中のプログラム自身が自発的に実行するものである。ユーザープログラムが OS を呼び出すことも、自ら CPU を明け渡すこともしなければ、こうしたソフトウェアの制御フローだけでは、カーネルが実行権を取り戻す機会は訪れない。

そこで必要になるのが、実行中のプログラムの協力に依存しない入口、すなわち**割り込みと例外の仕組み**である。以下では、実行中のプログラムからカーネルへ制御が管理された形で移ることを、総称して trap と呼ぶ。trap という語の分類はプロセッサによって必ずしも一致しないため、ここでは理解のための便宜的な総称として使っている。

## ハードウェアが用意する、事前登録された「非常口」

割り込みの仕組みは、CPU に備わった一群の「非常口」として考えるとわかりやすい。通常のプログラムは自身の命令の流れに沿って進む。周辺機器やタイマーにできるのは割り込み要求を出すことだけであり、PC を任意のアドレスに直接書き換えることはできない。CPU は通常、現在の命令を完了した時点で要求の有無を確認して受け付け、カーネルが事前に登録しておいた入口を通ってハンドラへ移る。

具体的には、プロセッサはカーネルが設定した割り込みベクタテーブルに従って、次の処理を行う。

1. 元の PC やステータスレジスタなど、復帰に必要な最小限の状態を保存する。
2. 必要に応じて、カーネルの特権レベルとカーネルスタックに切り替える。
3. ベクタテーブルから、対応するカーネルの入口を見つける。
4. 制御を入口のコードに渡す。

状態の保存、特権レベルの変更、入口へのジャンプといった重要な手順はプロセッサが自動的に行うが、入口のアドレスと処理のルールはあらかじめカーネルが設定している。入口から先で実行されるのは OS のコードである。

## カーネルに入る代表的な 3 つの理由

| 種類 | 発生するタイミング | 例 |
|---|---|---|
| Interrupt（割り込み） | 現在の命令とは非同期に、外部のハードウェアが発生させる | タイマーの満了、NIC のデータ受信 |
| System call（システムコール） | プログラムが専用の命令を実行し、自発的にカーネルのサービスを要求する | `read()`、`write()`、`fork()` |
| Exception（例外） | 現在の命令の実行に伴って同期的に発生する | ページフォールト、ゼロ除算、不正命令 |

**割り込みは「定期的にカーネルに入ること」と同じではない。** NIC やディスクなどのデバイスも不定期に割り込みを発生させる。周期的に発生しうるのは、そのうちのタイマー割り込みだけである。さらに現代の Linux は周期的なティックなしで動作することもある（tickless）ため、「周期性」は割り込みの仕組みそのものに必須の性質ではない。

システムコールは、プログラムが自発的にカーネルに入るものと理解できる。ただし実際のハードウェアでは、外部割り込みとまったく同じ命令や入口を使うとは限らない。たとえば現代の x86-64 では、通常 `syscall` 命令が使われる。

例外も、必ずしもプログラムの誤りを意味しない。ページフォールトは、必要なページがまだメモリに読み込まれていないことを示しているだけの場合もあり、カーネルが処理した後に元の命令を再実行できる。

## カーネルに入っても、プロセスが切り替わるとは限らない

ここが最も混同しやすい点である。**trap は CPU をカーネルに入れるだけであり、プロセスを切り替えるかどうかはスケジューラが決める。**

たとえば NIC が割り込みを発生させた場合、カーネルはデータを処理した後、直前まで実行していたプロセスにそのまま戻ることが多い。すぐに完了するシステムコールであれば、元のプロセスへ直接戻ることもできる。スケジューラがコンテキストスイッチを行うのは、現在のプロセスを実行し続けるべきでないとき、あるいは別のプロセスを実行するほうが適切なときだけである。

よくある契機は次のとおり。

- タイマーが満了し、現在のプロセスが十分に長く実行されたとカーネルが判断した。
- 現在のプロセスが `read()` などのシステムコールを実行し、データ待ちでブロックした。
- より優先度の高いプロセスが起床した。
- 現在のプロセスが自発的に CPU を明け渡した。

## プリエンプティブな切り替えで起きること

シングルコア CPU がプロセス A を実行しており、プロセス B も実行可能状態にあるとする。

```text
プロセス A のユーザーコード
    │
    │ タイマーが割り込み要求を発生
    ▼
CPU が復帰用の状態を自動的に保存し、カーネルの入口へ移る
    │
    │ カーネルが割り込みを処理し、スケジューラが B の実行を決定
    ▼
A のコンテキストを保存し、B のコンテキストを復元
    │
    │ カーネルからユーザーモードへ復帰
    ▼
プロセス B が前回停止した位置から実行を再開
```

コンテキストには PC だけでなく、スタックポインタ、汎用レジスタ、アドレス空間に関わる状態も含まれる。後で再び A が選ばれると、カーネルはこれらの状態を復元するため、A にとっては「少しのあいだ一時停止していた」だけのように見える。

つまり、タイマー割り込みは**プロセスの自発的な協力に頼らずに**カーネルが制御を取り戻す機会を提供し、スケジューラはその機会を使って切り替えるかどうかを決める。両者はプリエンプティブ・マルチタスクを支える重要な基盤だが、スケジューリングに至る入口はタイマー割り込みだけではない。

## 現時点での理解

仕組み全体は、次の一文に集約できる。

> CPU は、ハードウェアが定義する割り込み・例外・システムコールの入口を通じて、管理された形でカーネルに入る。カーネルは入った理由に応じた処理を行い、必要に応じてスケジューラが現在のプロセスを保存して別のプロセスを復元する。こうして複数のプロセスが交互に実行の機会を得る。

ここで本当に区別すべきなのは、**カーネルに入ること、スケジューリングを判断すること、コンテキストスイッチを実行すること**という 3 つの動作である。これらは続けて起こることが多いが、同じものではない。

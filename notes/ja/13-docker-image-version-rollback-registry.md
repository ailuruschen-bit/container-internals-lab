# Docker イメージの実践（5）：バージョンの置き換え、ロールバック、レジストリ

[English](../13-docker-image-version-rollback-registry.md) | [中文](../zh/13-docker-image-version-rollback-registry.md) | **日本語**

Spring Boot のイメージをビルドした後、よりデリバリーの過程に近い 2 つの問題を実験した。アプリケーションのバージョンをどのように更新・ロールバックするのか、そしてビルドしたイメージを異なる環境の間でどのように受け渡すのか、である。

今回の最も重要な気づきは、コンテナ化されたアプリケーションは通常、既存のコンテナの中でプログラムを更新するのではなく、新しいイメージから新しいコンテナを作成するということである。そしてレジストリが、それらの異なるバージョンのイメージの保存と配布を担う。

## 1. バージョンの更新は既存のコンテナを変更することではない

今回は 2 つの Spring Boot のイメージを順にビルドした。

```text
spring-lab:v1
spring-lab:v2
```

本番のコンテナが現在 `v1` を実行しているとき、`v2` をリリースする基本的な考え方は、古いコンテナに入って JAR を上書きすることではない。古いコンテナを停止・削除し、新しいイメージでコンテナを作成することである。

```bash
docker stop spring-prod
docker rm spring-prod

docker run -d \
  --name spring-prod \
  -p 127.0.0.1:8081:8080 \
  spring-lab:v2
```

ここで起きているのは、実行中のインスタンスの置き換えである。

```text
古いコンテナ：spring-lab:v1  ──→  停止して削除

新しいコンテナ：spring-lab:v2  ──→  作成して起動
```

元の `spring-lab:v1` のイメージはそのまま残しておける。必要な実行設定に互換性がある限り、同じ方法で `v2` を停止し、`v1` からコンテナを作り直せば、アプリケーションのバージョンをロールバックできる。

手元の実験が終わった時点で、`spring-prod` が実行しているのは次のイメージである。

```text
spring-lab:v2
```

## 2. なぜステートレスなサービスは置き換えやすいのか

アプリケーションのインスタンスが、長期にわたって保持すべき業務の状態を自身のコンテナの書き込み可能層に書き込まないのであれば、コンテナそのものを置き換えることができる。

```text
Container
    ├── アプリケーション：イメージから提供される
    ├── 実行設定：起動時に注入される
    └── 永続化する状態：外部のデータベース、ボリューム、その他のサービス
```

アプリケーションのコンテナを削除しても、新しいコンテナが外部の状態を読み直してサービスの提供を続けられる。このようなステートレスなアプリケーションでは、バージョンの移行は主に「どのイメージで新しいインスタンスを作るか」という問題になる。

ただし、「イメージを置き換えるだけでよい」が成り立つには、いくつかの条件がある。

- 設定、パスワード、環境ごとの差異を、実行時に改めて提供できる。
- データが古いコンテナの書き込み可能層だけに保存されていない。
- 新旧のバージョンが使う外部のデータ構造に互換性がある。
- 古いバージョンのイメージを引き続き取得できる。

特に注意すべきなのは、イメージのロールバックで戻せるのはアプリケーションだけであり、データベースは自動的にはロールバックされないということである。新しいバージョンが互換性のないデータベースのマイグレーションを実行していれば、古いイメージを再び実行しても、古いプログラムが正常に動くとは限らない。

### 単純な置き換えは無停止リリースではない

1 台のホストにコンテナが 1 つしかなく、新旧のコンテナがどちらもホストの同じポートを使う場合は、古いコンテナを停止してからでないと新しいコンテナを起動できず、その間に短い停止が生じる可能性がある。

リリース中もサービスを提供し続けたい場合は、通常次のことが必要になる。

- アプリケーションのレプリカを複数同時に実行する。
- 新旧のバージョンで異なる内部インスタンスやポートを使う。
- 新しいインスタンスにヘルスチェックを行う。
- ロードバランサーやオーケストレーションシステムを通じて、トラフィックを段階的に切り替える。

つまり、コンテナはバージョンの置き換えを簡単にしてくれるが、ローリングリリース、自動ロールバック、ゼロダウンタイムには、さらに上位のデプロイの仕組みが必要である。

## 3. タグとロールバック可能なバージョン

`v1` と `v2` によって、バージョンの関係は直感的にわかる。

```text
spring-lab:v1
spring-lab:v2
```

しかしタグは本質的に、別のイメージの内容を指し直せる名前である。再ビルドして同じ `v2` タグを再び使えば、後から見る `v2` が最初にリリースしたときの内容であるとは限らない。

ロールバックをより確実にするためには、次のようにできる。

- リリースごとに重複しないバージョンのタグを使う。たとえばバージョン番号やコミットの識別子である。
- デプロイ時に実際に使ったイメージのダイジェストを保存しておく。
- 意味があいまいで変わりうる `latest` だけに頼らない。

タグは人が読むのに便利で、ダイジェストはイメージの内容を正確に確認するのに向いている。どちらの方法を使うにせよ、古いバージョンがローカルやレジストリに保存されていて、クリーンアップのポリシーで削除されていないことが前提になる。

## 4. レジストリは何を解決するのか

開発マシンの Docker Engine にしか存在しないイメージは、ほかのサーバーから直接使うことができない。レジストリはイメージの保存と配布のためのサービスであり、Docker クライアントはそこへイメージを push したり、そこからイメージを pull したりできる。

三者の関係は、次のように簡単に表せる。

```text
開発または CI 環境
    │ docker push
    ▼
Registry
    │ docker pull
    ▼
テストまたは本番環境
```

レジストリはアプリケーションをコンパイルしないし、新しいイメージを受け取ったからといって実行中のコンテナを自動的に置き換えることもない。レジストリが担うのはイメージの内容の保存、命名、配布であり、ビルドとデプロイは引き続き Docker クライアント、CI/CD、あるいはオーケストレーションのプラットフォームが行う。

## 5. ローカルでレジストリを動かす

今回の実験では、公式の `registry:3` イメージをそのまま使った。

```bash
docker run -d \
  --name registry-lab \
  -p 127.0.0.1:5000:5000 \
  registry:3
```

コンテナ内のレジストリは 5000 番ポートで待ち受け、OrbStack がそれを macOS の `127.0.0.1:5000` に公開する。

レジストリの API を通じて、今回の実験のリポジトリを確認できる。

```bash
curl http://127.0.0.1:5000/v2/_catalog
```

手元では現在、次の結果が返ってくる。

```json
{"repositories":["spring-lab"]}
```

さらに `spring-lab` のタグを確認する。

```bash
curl http://127.0.0.1:5000/v2/spring-lab/tags/list
```

現在の結果は次のとおりである。

```json
{"name":"spring-lab","tags":["v1"]}
```

これらの HTTP API は実験の結果を観察するのに便利だが、日常的なイメージのアップロードとダウンロードには、やはり `docker push` と `docker pull` を使う。

## 6. なぜ先にイメージにレジストリのプレフィックスを付けるのか

完全なイメージの参照は、次のように簡略化できる。

```text
[レジストリのアドレス/][名前空間/]リポジトリ[:タグ]
```

ローカルのイメージの元の名前は次のとおりである。

```text
spring-lab:v1
```

ローカルのレジストリに push するには、同じイメージに、サービスのアドレスを含むタグを追加する必要がある。

```bash
docker image tag \
  spring-lab:v1 \
  localhost:5000/spring-lab:v1
```

ここでの `localhost:5000` は、対象のレジストリがどこにあるかを Docker に伝えている。その後ろの `spring-lab:v1` は、そのレジストリ内のリポジトリとタグを表している。

`docker image tag` は、ローカルに別の参照名を追加するだけであり、イメージをアップロードすることも、ファイルシステムを丸ごとコピーすることもない。

```text
spring-lab:v1
          └──────────────┐
                         ▼
                   同一のイメージ ID
                         ▲
localhost:5000/spring-lab:v1
          └──────────────┘
```

## 7. Push、削除、Pull

レジストリ用のタグを追加したら、使うのは `push` である。

```bash
docker push localhost:5000/spring-lab:v1
```

`pull` ではない。2 つのコマンドの方向は逆である。

```text
docker push  ローカルの Docker Engine ──→ Registry
docker pull  Registry ──→ ローカルの Docker Engine
```

push のとき、レジストリはイメージのマニフェスト、設定、ファイルシステムのレイヤーを保存する。内容が同じで、レジストリがすでに持っているレイヤーは毎回保存し直す必要がないため、出力に一部のレイヤーがすでに存在すると表示されることがある。

### ローカルのイメージを削除して pull し直す

これらのイメージに依存しているコンテナがないことを確認したら、ローカルの参照を削除できる。

```bash
docker image rm localhost:5000/spring-lab:v1
docker image rm spring-lab:v1
```

ここで 2 つのタグを両方削除するのは、どちらも同じローカルのイメージを指している可能性があるからである。レジストリ用のタグだけを削除しても、短い名前の `spring-lab:v1` は残り、下層のイメージデータも存在し続ける可能性がある。そうなると、今回の pull だけでは、レジストリからイメージを復元できることを十分に証明できない。

レジストリから pull する。

```bash
docker pull localhost:5000/spring-lab:v1
```

取得されるのは、レジストリの完全なアドレスを含む参照である。

```text
localhost:5000/spring-lab:v1
```

元の短い名前を引き続き使いたい場合は、タグを付け直せばよい。

```bash
docker image tag \
  localhost:5000/spring-lab:v1 \
  spring-lab:v1
```

ローカルのイメージを削除しても、レジストリにすでに push した内容は削除されない。逆に、レジストリのコンテナやそのストレージを削除すれば、リモートの内容が失われる可能性がある。

## 8. レジストリのデータも永続化が必要

レジストリはデータをコンテナ内の `/var/lib/registry` に保存する。今回実行した公式イメージはこのパスに Docker のボリュームを使っているため、コンテナのファイルシステムの外に独立したストレージが存在する。

ストレージの名前とライフサイクルをより明確にするために、レジストリを作成するときに名前付きボリュームを指定できる。

```bash
docker volume create registry-data

docker run -d \
  --name registry-lab \
  -p 127.0.0.1:5000:5000 \
  --mount type=volume,source=registry-data,target=/var/lib/registry \
  registry:3
```

こうしておけば、レジストリのコンテナを置き換えるときに、同じ `registry-data` を再びマウントできる。ただし、ボリュームが解決するのは単一ホストでの実験におけるコンテナのデータの独立性だけであり、バックアップ、高可用性、災害復旧の能力が備わったことを意味するわけではない。

## 9. ローカルの実験から複数の環境へ

ローカルでは `localhost:5000` を使っているが、このアドレスを自分のレジストリとして理解できるのは現在のホストだけである。開発、テスト、本番の各環境でイメージを共有するには、それらすべての環境からアクセスできるネットワークアドレスをレジストリが持っている必要がある。たとえば次のようなものである。

```text
registry.example.com/team/spring-lab:v1
```

各環境が同じ完全なイメージの参照を使えば、同じビルド成果物を中心にテストとデプロイを進められる。

```text
一度だけビルドする
    ↓
Registry に push する
    ↓
テスト環境で pull して検証する
    ↓
本番環境で同じバージョンまたはダイジェストを pull する
```

ここで移しているのは、開発マシンで実行中のコンテナではなく、不変のイメージの内容である。各環境は引き続き、それぞれの環境変数、シークレット、ネットワーク、永続ストレージを用意する必要がある。

ローカルの認証なしの HTTP レジストリは、実験にしか適していない。実際にほかのマシンへ公開するなら、少なくとも次の点を考慮する必要がある。

- TLS による暗号化と信頼できる証明書。
- ログイン認証ときめ細かなアクセス権限。
- イメージの保持期間とガベージコレクションのポリシー。
- 永続ストレージ、バックアップ、可用性。
- セキュリティスキャン、監査、ネットワークのアクセス制御。

企業は Distribution のレジストリを自分で運用することも、AWS ECR などの成熟したマネージドサービスを使うこともできる。マネージドサービスを使えば、レジストリのサーバー、ストレージ、可用性に関する保守の負担が減り、クラウドプラットフォームの ID・権限管理、監査、スキャンの機能とも組み合わせられる。Docker クライアントとの基本的なやり取りは、引き続き認証、タグ付け、push、pull である。

## 10. 今日得られた理解

今回の実験で、イメージは「手元のマシンのビルド成果物」から「環境をまたいで受け渡せるバージョン」になった。

```text
ソースコード
  │ build
  ▼
spring-lab:v1
  │ tag + push
  ▼
Registry
  │ pull
  ├──────────→ テスト環境
  └──────────→ 本番環境
                  │
                  ├── v2 で新しいコンテナを作成：アップグレード
                  └── v1 で新しいコンテナを作成：ロールバック
```

ステートレスなアプリケーションでは、コンテナそのものはいつでも新しいバージョンに置き換えられ、本当に長期間保持すべき状態はコンテナの外にある。レジストリは、各サーバーでプロジェクトを再コンパイルしなくても、デプロイ先の環境が指定されたイメージを取得できることを保証する。

したがって、完全なバージョン管理とは、ローカルにいくつかのタグを残しておくことだけではない。次のものを同時に管理することである。

- 各バージョンに対応する、明確なイメージの参照やダイジェスト。
- レジストリから引き続き取得できる過去のイメージ。
- そのバージョンに合った実行設定。
- イメージのロールバックでは元に戻せない、データ構造の変更。
- 新しいコンテナの起動からトラフィックの切り替えまでのリリースの流れ。

イメージの置き換えによって、アプリケーションのアップグレードとロールバックの操作は簡単になる。しかし信頼できるリリースは、取り違えようのないバージョン、外部化された状態、データの互換性、そしてレジストリとデプロイの流れそのものの安定性に支えられている。

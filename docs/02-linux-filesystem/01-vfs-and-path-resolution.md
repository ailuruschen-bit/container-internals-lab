# 1. The Virtual File System and Path Resolution

## The problem: many filesystems, one API

A Linux system uses many kinds of filesystems at once:

- `ext4` or `xfs` on a disk partition;
- `tmpfs`, which stores files in memory;
- `nfs`, which stores them on another machine;
- `proc` and `sysfs`, whose "files" are generated by the kernel on demand
  (Chapter 01 §4);
- `overlay`, which combines other directories (Chapter 08).

Yet `cat` uses the same `openat()` and `read()` calls for all of them. It does
not know or care which filesystem is involved.

## The Linux abstraction: the VFS

The **Virtual File System (VFS)** is the kernel layer between the file-related
system calls and the concrete filesystem implementations. It defines a common
object model and a set of operations (function pointer tables). Each
filesystem implements those operations in its own way.

```text
 openat  read  write  stat  mkdir  mount ...          system calls
    │      │     │      │     │      │
    ▼      ▼     ▼      ▼     ▼      ▼
┌──────────────────────────────────────────────┐
│                     VFS                      │  path lookup, permission checks,
│  file   dentry   inode   super_block   mount │  caches, mount tree
└──────────────────────────────────────────────┘
    │          │          │          │
    ▼          ▼          ▼          ▼
  ext4       tmpfs      proc      overlay            filesystem implementations
    │                               │
  block device                  other directories
```

### The four core VFS objects

| Object | Represents | Lifetime | Chapter 01 connection |
|---|---|---|---|
| `super_block` | One **instance** of a filesystem, e.g. "the ext4 filesystem on `/dev/vda1`" or "this particular tmpfs" | From mount until the last user is gone | |
| `inode` | One **file object** within a filesystem: its type, owner, mode, size, timestamps, and where its data is | As long as it has a name or anyone holds it open | the file at the bottom of the fd model |
| `dentry` | One **name in a directory** linking to an inode ("directory entry"), cached for fast lookup | Cache-managed | |
| `file` | One **open file description**: offset and status flags | From `open()` until the last fd referring to it is closed | exactly §5's "open file description" |

The separation between inode and dentry explains familiar behavior:

- **Hard links.** Two names (dentries) can point to one inode. The inode's link
  count (`nlink`) counts the names. `rm` calls `unlink()`, which removes a
  name, not a file.
- **Deleting an open file.** When the last name is removed but a process still
  holds the file open, the inode and its data survive until the last open file
  description is closed. Chapter 01 Lab 05 recovered a deleted binary through
  `/proc/<pid>/exe` for this reason.
- **Metadata is per inode, not per name.** Permission bits and owner live on the
  inode, so all hard links share them.

An inode number is unique only **within one filesystem instance**. The pair
(device ID, inode number) identifies a file on the whole system. `stat` shows
both.

## Mounts join filesystems into one tree

Each filesystem instance has its own internal directory tree with its own root
directory. The VFS combines these separate trees into the single tree you see
starting at `/`. The glue is the **mount**: "the root of filesystem instance B
appears at directory `/x` of filesystem instance A". [Section 2](02-mounts.md)
covers mounts in detail. For path resolution, one fact is enough: when lookup
reaches a directory that has something mounted on it, it continues in the root
of the mounted filesystem instead.

## Path resolution

Converting a path string to a `(mount, dentry)` pair is called **path
resolution** or **path walking**, implemented in the kernel file `fs/namei.c`.
Simplified:

```text
resolve(path) for the calling task:
    if path starts with "/":
        start = task->fs->root          the process's root directory
    else:
        start = task->fs->pwd           the process's working directory
        (or the directory fd given to openat)

    for each component in path:
        if component == ".":   stay
        if component == "..":
            if current == task->fs->root:  stay        ← cannot go above own root
            elif current is the root of a mount: go to the mountpoint, then its parent
            else: go to the parent dentry
        else:
            look up the name in the current directory (dentry cache, else filesystem)
            check search (x) permission on the directory
            if something is mounted on the result: move to the root of that mount
            if the result is a symlink: resolve its target (with a depth limit)
    return (mount, dentry)
```

Look at the two lines that use `task->fs`. Every absolute path starts at the
calling process's **root directory**, and `..` stops there. These are fields of
the process (the `fs_struct` from Chapter 01 §1), inherited across `fork()` and
preserved across `execve()`.

Therefore:

> The meaning of `/` is not global. It is a property of each process.

Almost every process on a host shares the same root directory, so this is
invisible in everyday use. `/proc/<pid>/root` exposes it. Chapter 07 shows how
`chroot()` and `pivot_root()` change it, and why `chroot()` alone is not a
security boundary.

Also note what path resolution uses besides the root: the **mount tree**. Two
processes with the same root directory but different mount trees can resolve
the same path to different files. Giving a process its own mount tree is
exactly what a mount namespace does (Chapter 03).

## Observing VFS objects from user space

| Question | Tool | Underlying syscall |
|---|---|---|
| Which inode, device, link count, owner? | `stat file` | `statx()` |
| Which filesystem type holds this path? | `stat -f -c %T path`, `df -T path` | `statfs()` |
| Which mount contains this path? | `findmnt -T path` | reads `/proc/self/mountinfo` |
| What is this process's root? | `readlink /proc/<pid>/root` | procfs |
| How was a path resolved step by step? | `namei -l path` | repeated `lstat()` |

## Why this matters for containers

- A container's filesystem is still made of ordinary VFS objects. There is no
  "container file". An image layer is a directory tree on some host
  filesystem; the container sees it through mounts.
- The two per-process inputs to path resolution, **the root directory** and
  **the mount tree**, are exactly the two things container runtimes change.
- Inode and link semantics explain container-specific surprises, such as why a
  bind-mounted single file does not see updates made by editors that replace the
  file with a new inode (Lab 03 of this chapter).

## Further Reading

- Kernel docs: [Overview of the Linux Virtual File System](https://docs.kernel.org/filesystems/vfs.html)
  — the official description of `super_block`, `inode`, `dentry`, and `file`
  operations. Read the introduction and the "struct super_operations",
  "struct inode_operations", and "struct file_operations" headings; skip the
  per-method detail.
- Kernel docs: [Pathname lookup](https://docs.kernel.org/filesystems/path-lookup.html)
  — Neil Brown's detailed, readable explanation of `fs/namei.c`, including
  mount crossing and `..` handling. The best source for the pseudocode above.
- [`path_resolution(7)`](https://man7.org/linux/man-pages/man7/path_resolution.7.html)
  — the user-space view of the same algorithm in two pages: root, working
  directory, `..`, symlinks, and permission checks.
- [`inode(7)`](https://man7.org/linux/man-pages/man7/inode.7.html) — every
  field `stat` reports and what it means.
- [`unlink(2)`](https://man7.org/linux/man-pages/man2/unlink.2.html) — the
  precise rule for when a file's data is actually freed.
